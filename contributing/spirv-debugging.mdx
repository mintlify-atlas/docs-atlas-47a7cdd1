When debugging SPIR-V issues generated by Rust-GPU, it is often necessary to reduce the binary to a minimal, self-contained reproducer that can be shared with the Rust-GPU team or with upstream tool maintainers. A minimal reproducer is far easier to reason about than a full shader, removes any proprietary code from the report, and helps pinpoint whether the bug is in Rust-GPU's code generation, in a downstream validator, or in a driver. This page covers the tools and the step-by-step process for creating one.

## Prerequisites

You will need [SPIRV-Tools](https://github.com/KhronosGroup/SPIRV-Tools#downloads) installed and available on your `PATH`. The relevant binaries are:

- **`spirv-as`** — assembles human-readable SPIR-V text (`.spvasm`) into a binary (`.spv`)
- **`spirv-val`** — validates a SPIR-V binary against the specification
- **`spirv-cross`** — cross-compiles SPIR-V to GLSL, HLSL, or MSL

Download pre-built binaries from the [SPIRV-Tools releases page](https://github.com/KhronosGroup/SPIRV-Tools#downloads).

## SPIR-V Assembly Template

SPIR-V requires a certain amount of boilerplate to be considered valid. The template below creates a single empty vertex entry-point with a single floating-point constant — the smallest useful starting point when writing a reproducer from scratch.

```spirv
; bug.spvasm
OpCapability Shader
OpCapability VulkanMemoryModel
OpMemoryModel Logical Vulkan

; == Entry-points ==
OpEntryPoint Vertex %vert_fn "vert"

; == Types ==
%void = OpTypeVoid
%f32 = OpTypeFloat 32

; Function Types
%void_fn = OpTypeFunction %void

; == Constants ==
%f32_1 = OpConstant %f32 1

; == Functions ==
%vert_fn = OpFunction %void None %void_fn
  %block = OpLabel
    OpReturn
OpFunctionEnd
```

Each section serves a distinct purpose:

| Section | Purpose |
|---|---|
| `OpCapability` | Declares which SPIR-V capabilities the module uses |
| `OpMemoryModel` | Specifies the addressing and memory model |
| `OpEntryPoint` | Declares a named shader entry point and its execution model |
| `OpType*` | Defines all types used in the module |
| `OpConstant` | Declares constant values |
| `OpFunction` / `OpFunctionEnd` | Contains the actual executable instructions |

Start from this template and add the smallest set of instructions that reproduces the problem you are investigating.

## Minimization Steps

<Steps>
  <Step title="Write or extract SPIR-V assembly">
    Either write your reproducer from scratch using the template above, or extract SPIR-V assembly from a Rust-GPU build using the `--dump-post-link` codegen argument (see [Using Codegen Args for Debugging](#using-codegen-args-for-debugging)). Save the file as `bug.spvasm`.
  </Step>

  <Step title="Assemble the binary">
    ```bash
    spirv-as ./bug.spvasm
    ```
    This produces `out.spv` — a binary SPIR-V module — in the current directory.
  </Step>

  <Step title="Validate the binary">
    ```bash
    spirv-val out.spv
    ```
    `spirv-val` checks the binary against the SPIR-V specification. Fix any reported errors before proceeding; a reproducer that is itself invalid is not useful.
  </Step>

  <Step title="Cross-compile to verify the issue">
    Use `spirv-cross` to compile the validated binary to a human-readable shading language and confirm the problem is visible there:

    ```bash
    # GLSL (default)
    spirv-cross out.spv

    # HLSL
    spirv-cross --hlsl out.spv

    # MSL (Metal)
    spirv-cross --msl out.spv

    # Vulkan-flavoured GLSL
    spirv-cross -V out.spv
    ```

    Once you have the smallest `.spvasm` that still demonstrates the bug, you have a shareable reproducer ready for a bug report.
  </Step>
</Steps>

## Using Codegen Args for Debugging

Rust-GPU exposes a set of codegen arguments via the `RUSTGPU_CODEGEN_ARGS` environment variable (documented on the [Codegen Args](/spirv-builder/codegen-args) reference page) that are invaluable when investigating code-generation issues.

The two most useful flags for capturing Rust-GPU output are:

- **`--dump-post-link`** — writes out the final linked SPIR-V module(s) to disk after the linking step. This gives you the raw SPIR-V that Rust-GPU produced before any further processing, in a form you can feed directly to `spirv-val` or `spirv-cross`.
- **`--dump-spirt-passes`** — dumps the internal SPIR-T IR after each optimisation pass.

<Tip>
`--dump-spirt-passes` produces a `.spirt.html` file that renders the SPIR-T IR as a colour-coded, human-readable HTML report. Opening this in a browser is often the fastest way to understand what the optimiser did (or failed to do) to your shader.
</Tip>

Set the arguments before running your build:

```bash
RUSTGPU_CODEGEN_ARGS="--dump-post-link=. --dump-spirt-passes=." cargo build
```

## Filing Bug Reports

When opening an issue for a SPIR-V code generation bug, please include:

- The **Rust-GPU version** (or commit SHA if building from source)
- The **Rust nightly toolchain version** (`rustc --version`)
- A **minimal `.spvasm` reproducer** produced using the steps above
- The **dumped SPIR-V** from `--dump-post-link` if the issue is in the generated output rather than in assembly you wrote by hand
- The **exact error message** from `spirv-val`, `spirv-cross`, or your driver/validator
